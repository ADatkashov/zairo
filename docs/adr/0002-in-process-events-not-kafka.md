# ADR-0002: Внутрипроцессные доменные события, не Kafka

## Статус
Принято — 2026-08-19

## Контекст
Модулям (`booking`, `notifications`, `reviews` и т.д.) нужно реагировать на
события друг друга (например: "booking подтверждён" → отправить
уведомление), не создавая прямых compile-time зависимостей между
bounded-context модулями в обе стороны.

## Решение
Используем Spring `ApplicationEventPublisher` + `@TransactionalEventListener`
внутри одного процесса `platform-api`. Kafka (или любой другой брокер
сообщений) не подключается.

## Почему
- Это modular monolith (см. ADR-0001) — все модули уже в одном процессе,
  сетевой брокер сообщений не нужен для доставки событий внутри процесса.
- `@TransactionalEventListener` даёт "событие публикуется только если
  транзакция закоммитилась" без дополнительной инфраструктуры (outbox,
  брокер, consumer groups).
- Kafka добавляет операционную сложность (кластер, схемы сообщений,
  мониторинг лагов), не оправданную текущим масштабом.

## Когда пересматривать
Когда появится модуль/сервис, который реально живёт в отдельном процессе
(например, отдельный recommendation/search-сервис или интеграция с внешней
системой, которой нужна durable-очередь) — тогда Kafka или другой брокер
вводится точечно для этой интеграции, а не как замена всей внутренней шине.

## Альтернативы
- Kafka с самого начала — отклонено: преждевременная инфраструктура.
- Outbox pattern с отдельной таблицей — отклонено пока: усложнение без
  текущей необходимости при отсутствии межпроцессных consumers.
