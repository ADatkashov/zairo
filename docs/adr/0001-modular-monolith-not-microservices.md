# ADR-0001: Modular monolith, не микросервисы

## Статус
Принято — 2026-08-19

## Контекст
Backend разбит на bounded-context модули (`auth`, `users`, `providers`,
`services`, `booking`, `payments`, `reviews`, `notifications`, `search`),
но все они собираются в один деплой-юнит `platform-api` (Gradle
multi-module в рамках одного `build.gradle.kts`-графа), а не как отдельные
сервисы за сетью.

## Решение
На старте проекта (MVP, один vertical, один инстанс) используем **modular
monolith**: границы модулей — это границы Java-пакетов и Gradle-подпроектов,
а не границы процессов/сетевых сервисов.

## Почему
- Нет команды из нескольких независимых бэкенд-групп, которым нужна
  раздельная деплой-каденция — единственный developer/small team только
  замедлится на operational overhead микросервисов (service discovery,
  распределённые транзакции, наблюдаемость через сеть).
- Модульные границы (по bounded context) сохраняются на уровне кода —
  переход к микросервисам позже, если понадобится, это извлечение модуля
  в отдельный деплой, а не переписывание границ с нуля.
- Метрика проекта — скорость запуска нового vertical (см. Factory Blueprint
  KPI), а не независимое масштабирование каждого bounded context.

## Когда пересматривать
Когда конкретный модуль (например, `search` или `notifications`) реально
упрётся в независимое масштабирование или в необходимость отдельной
деплой-каденции — тогда извлекается точечно, не весь backend разом.

## Альтернативы
- Микросервисы с самого начала — отклонено: преждевременная сложность для
  текущего масштаба (один vertical, вероятно один инстанс на первое время).
