# Защита HTTP API

## Как устроено сейчас
1. **Токены.** `JwtAuthFilter` (клиенты и бизнес) и `PlatformAuthFilter` (консоль платформы, свой секрет)
   кладут `userId`/`role` в атрибуты запроса. Невалидный токен = как будто токена нет.
2. **«Закрыто по умолчанию».** `RequireAuthenticationInterceptor` отвечает 401 на любой эндпоинт с
   `@SecurityRequirement` без валидного токена — до валидации тела и до обращения к БД.
   Кто именно вызывает и что ему можно (владелец, роль) по-прежнему проверяют контроллеры
   (`CurrentUser`, `PlatformCurrentAdmin`, `ProviderOwnership`).
3. **Явный список публичных эндпоинтов.** `EndpointAuthPolicyTests` падает, если у эндпоинта нет
   `@SecurityRequirement` и его нет в `PUBLIC` — новый эндпоинт не может стать открытым случайно.
   Тот же тест проверяет, что каждый защищённый эндпоинт отвечает анонимному запросу 401.
4. **Лимиты.** `AuthRateLimitFilter` (по IP и, где есть, по email): вход, регистрация, восстановление
   пароля, обновление токена, вход в консоль платформы. 429 + `Retry-After`. Дополняет блокировку
   аккаунта по email при входе (`LoginAttemptLimiter`) и лимиты OTP. Счётчики в памяти
   (один инстанс, ADR-0001); при нескольких инстансах нужен общий стор.
   Выключатель: `app.rate-limit.enabled` (в интеграционных тестах выключен).

## Как добавить эндпоинт
Защищённый — `@SecurityRequirement(name = "bearerAuth")` + проверка владения в контроллере.
Публичный — добавить строку в `EndpointAuthPolicyTests.PUBLIC` и объяснить в ревью, почему.
