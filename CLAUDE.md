# Инструкции для Claude по этому репозиторию

## Ветки и git-workflow (с 2026-08-26)

Порядок веток: **`develop` → `test` → `master`**.

- **`develop`** — активная рабочая ветка. Коммитить и пушить сюда
  сразу, без отдельного запроса подтверждения на каждый коммит.
- **`develop` → `test`**: через Pull Request, который создаёт и мержит
  **сам пользователь**. Claude туда не мержит.
- **`test` → `master`**: тоже сам пользователь, с полной проверкой.
  Claude туда не мержит.

## Автотесты (с 2026-10-12)

**Любое изменение кода пишется сразу вместе с автотестами**, в том же коммите:

- **backend** (`backend/*`, Kotlin/Spring): тест на новую или изменённую
  логику/эндпоинт в `src/test` того же модуля.
- **frontend** (`apps/user_app`, `apps/business_admin`, `apps/platform_admin`,
  `packages/*`): unit/widget-тест в `test/` рядом с изменённой фичей.
- Багфикс начинается с теста, который воспроизводит баг.
- Перед коммитом тесты затронутого модуля/приложения должны проходить;
  если запустить их нельзя (нет SDK, нет Docker), прямо сказать об этом.
- Не отключать и не пропускать тесты, чтобы получить зелёный результат.
- **Цель — 100 % покрытия написанного вручную кода** (сгенерированный код и
  `l10n` не считаются). Покрытие измеряется в CI и не должно падать: порог
  каждого Flutter-пакета лежит в `config/coverage-thresholds.json` и только
  растёт (`python3 scripts/check_coverage.py <пакет> --update` после
  `flutter test --coverage`). Никогда не снижать порог ради зелёной сборки.
- Исключать код из покрытия можно только явно и с причиной (список в
  `scripts/check_coverage.py`), а не молча.

Это правило будет пополняться другими заметками по мере необходимости.
